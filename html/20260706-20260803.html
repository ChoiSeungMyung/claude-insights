Claude Code를 어떻게 쓰나

큰 스펙을 넘기고 손을 떼는 대신, 촘촘한 검증 루프로 일합니다. 38개 세션에 걸쳐 Claude의 결론을 반복해서 교정했고, 지배적인 마찰 패턴은 'wrong_approach'(17건)와 Claude가 스스로의 진단을 번복하는 것의 조합입니다. WorkManager 클럭 드리프트 버그, 알람 지속성 예측, 연결 감지 로직에서 성급한 근본 원인 주장을 반박했고 Claude가 자신의 단정을 실제 기기 출력과 대조하게 만들었습니다. 이것이 결정적인 특징입니다. Claude의 확신에 찬 결론을 받아들일 답이 아니라 확인해야 할 가설로 다룹니다. 다만 높은 'likely_satisfied' 수치(100)가 17건의 불만족과 잦은 교정 마찰과 나란히 있다는 점에서, 만족도 숫자만 보면 실제보다 매끄러워 보입니다. 좋은 결과는 깔끔한 첫 패스가 아니라 다투는 반복을 거쳐 나왔습니다.

핵심 패턴: Claude의 확신에 찬 진단을 검증되지 않은 가설로 다룹니다 — 빠르게 중단시키고, 양쪽의 전제를 교정하며, 첫 패스 결론을 받아들이는 대신 정확한 산출 범위와 구조를 강제합니다.

인상적이었던 작업

약 한 달간 38개 세션 동안 Claude Code를 주로 Android/Kotlin 작업에 사용했고 Bash와 Edit 활동이 많았습니다. 가장 좋은 결과는 무작정 코드를 생성하는 쪽이 아니라 조사 중심·리뷰 중심 워크플로우에서 나왔습니다.

기기 검증을 동반한 근본 원인 디버깅
디버깅을 표면 증상에서 멈추지 않고 실제 근본 원인까지 일관되게 밀어붙였습니다. 예를 들어 새벽 3시 업데이트 실패는 WorkManager 클럭 드리프트로 추적되어 AlarmManager 방식으로 교체되고 실기기에서 검증됐습니다. Claude의 첫 진단을 받아들이지 않았고, 알람 지속성에 대한 예측이 틀렸을 때 실제 기기 출력으로 반증했습니다. 이 세션들이 그럴듯하지만 틀린 수정 대신 완전 달성에 도달한 이유입니다.
Claude의 전제와 범위를 교정
많은 세션에서 Claude의 실수를 잡아 되돌렸습니다. 잘못된 diff base로 계산된 리뷰(develop 대신 main), ViewModel에 잘못 놓인 타임스탬프 로직, 과설계된 에러 메시지, Slack이 GitHub Projects를 기본 구독한다는 잘못된 주장이 그 예입니다. Claude의 출력을 결론이 아니라 따져볼 초안으로 다룬 것이 여러 '대부분 달성' 세션을 쓸 만한 결과로 바꿔놓았습니다.
스택 PR과 분석 전용 가드레일
산출 규율을 강제했습니다. 정리 작업을 하나의 큰 PR 대신 독립적으로 컴파일되고 따로 리뷰 가능한 4개의 스택 PR로 쪼개라고 요구했고, 읽기 전용 조사나 설계 의견 작업에서 Claude가 코드 편집으로 흘러갈 때마다 중단시켰습니다. 이런 제약을 미리 걸어둔 덕분에 리뷰가 초점을 유지했고 원치 않는 코드 변경을 막았습니다.

문제가 생기는 지점

주된 마찰은 Claude가 성급하게 결론으로 건너뛰고, 무엇을 원하는지 확인하기 전에 행동(편집, 탐색, 범위 설정)하는 데서 나옵니다. 그래서 반복적으로 중단시키고 교정해야 했습니다.

성급하거나 번복되는 진단
Claude가 근거 없는 확신으로 근본 원인을 단정했다가, 사용자가 반박하거나 기기 출력이 주장과 어긋나자 철회하기를 반복했습니다. 결론을 확정하기 전에 확신 수준을 밝히고 실제 출력과 대조하도록 요구할 수 있습니다.
  • Claude가 클럭 롤백을 버그로 규정했다가 철회했고, 배치 타이밍 권고도 사용자의 반박이 있고 나서야 거둬들여 왕복 라운드를 소모했습니다.
  • 패키지 재설치 후 알람 지속성에 대해 두 번 잘못 예측했고 실제 기기 출력이 이를 반증해, WiFi·업데이트 디버깅 세션이 길어졌습니다.
범위 확인 없이 행동하기
분석이나 리뷰만 원했을 때 Claude가 코드 편집, 더 넓은 갭 분석, 백그라운드 탐색 에이전트로 옮겨가서 중단시켜야 했습니다. 앞머리에 '분석만, 편집 금지'라고 밝히면 도움이 되지만, 요청이 질문일 때 Claude가 기본적으로 읽기 전용이어야 하는 문제이기도 합니다.
  • @Provides/@Binds 조사와 Matrix 프로토콜 리뷰에서 Claude가 코드를 수정하거나 범위를 넓히기 시작해, 분석만 원한다고 다시 말하며 중단시켜야 했습니다.
  • Claude가 백그라운드 탐색 에이전트를 띄우고 폴링해서, 이를 중단하고 종료시켰습니다.
첫 패스의 잘못된 구조와 과설계
Claude의 초기 산출물이 잘못된 파일 구조, 잘못된 diff base, 과도한 추상화를 쓰는 경우가 많아 재작업이 필요했습니다. 목표 구조(스택 PR, 파일별 프리뷰, PR base 브랜치)를 첫 메시지에 명시하면 이런 번복이 줄어듭니다.
  • PR base가 develop인데 Claude가 main...HEAD로 리뷰를 계산해, 인라인 코멘트 8개 중 7개가 거부되고 전면 재작업이 필요했습니다.
  • 작은 스택 PR을 원했는데 Claude가 모든 정리 작업을 하나의 PR로 몰았고, 프리뷰를 각 컴포저블 옆이 아니라 통합 파일에 몰아넣어 둘 다 다시 해야 했습니다.

한 리뷰는 base가 develop인데 main...HEAD로 계산해 코멘트 8개 중 7개가 거부됐고, 다른 하나는 너무 장황해 실행할 수 없었으며, 두 건은 하드코딩 문자열과 Compose 문제를 잡도록 사용자가 밀어붙여야 했습니다.
사용자가 최소 한 세션에서 이를 전역 정리 규칙으로 설정했고 다른 곳에서도 스택 정리 작업을 해, 반복되는 선호임을 보여줍니다.

Claude Code에 그대로 붙여넣으면 알아서 설정해줍니다.

Custom Skills
고정된 워크플로우를 실행하는, 마크다운으로 정의된 재사용 /명령.
왜 당신에게 유용한가: 커밋/PR/리뷰 루프가 대부분의 세션에서 반복되고(commit_and_pr, code_review, iterative_review_refinement) 이미 /insights와 /simplify를 만들어 썼습니다. diff base와 출력 형식을 고정한 /review 스킬이 있으면 장황함과 잘못된 base로 인한 재작업이 사라집니다.
mkdir -p .claude/skills/review && cat > .claude/skills/review/SKILL.md <<'EOF' # /review 1. PR base 브랜치를 확인: gh pr view --json baseRefName -q .baseRefName 2. base...HEAD 만 diff. main을 가정하지 말 것. 3. 출력: 발견 사항 최대 10개, 심각도별 그룹화, 각 항목에 file:line과 한 줄 수정안. 4. 반드시 점검: 하드코딩 UI 문자열, Compose 리컴포지션/key 오용, 제거되지 않은 디버그 로그. 5. 코드를 편집하지 말 것. 보고만 할 것. EOF
Hooks
편집 후 같은 라이프사이클 이벤트에 자동 실행되는 셸 명령.
왜 당신에게 유용한가: 두 세션에서 리팩토링 도중 빌드 오류가 드러났고(metroViewModel 가시성, MVI 리팩토링) Gradle/Kotlin 작업이 많습니다. 편집 후 자동 빌드·컴파일 체크가 있으면 당신에게 도달하기 전에 잡힙니다.
// .claude/settings.json { "hooks": { "PostToolUse": [ { "matcher": "Edit|Write", "hooks": [ { "type": "command", "command": "./gradlew compileDebugKotlin -q || echo 'BUILD BROKEN'" } ] } ] } }
MCP Servers
Model Context Protocol로 GitHub 같은 외부 도구에 Claude를 연결.
왜 당신에게 유용한가: gh로 PR·Project 작업을 자주 하고(issue #26, Project #12, Copilot Action) Slack/Projects 연동에 대한 잘못된 전제에 부딪혔습니다. GitHub MCP 서버는 잘못된 가정을 부른 임기응변식 gh 호출 대신 구조화되고 검증 가능한 접근을 제공합니다.
claude mcp add github -- npx -y @modelcontextprotocol/server-github

앞으로의 전망

사용 양상을 보면 리뷰와 디버깅 작업이 많고 Claude가 자주 성급한 결론에 도달했습니다. 따라서 가장 큰 이득은 자율성을 더하는 쪽이 아니라 단정 전에 검증을 강제하는 워크플로우에서 나옵니다.

결론 전에 검증을 게이트로 둔 진단
가장 반복된 마찰(잘못된 접근 17건, 요청 오해 9건, 그리고 클럭 드리프트·알람 지속성·패키지 조회에서의 반복적 자기 번복)은 Claude가 기기나 코드 증거를 확인하기 전에 근본 원인을 단정한 데서 나왔습니다. 수정안을 제안하기 전에 버그를 재현하고 구체적 증거를 인용하도록 요구하는 워크플로우라면, 거의 모든 디버깅 세션에서 치른 교정 라운드가 사라집니다. 더 큰 에이전트가 아니라 규율의 변화입니다.
