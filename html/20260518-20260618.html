무엇이 어긋나는가

당신의 주된 마찰은 Claude가 디버깅 중 성급한 결론으로 건너뛰는 것, 요청하지 않은 자율적 행동을 하는 것, 그리고 권한/셸 따옴표 문제로 막히는 것에서 비롯됩니다.

디버깅 중 성급한 근본 원인 단정
Claude가 잘못된 근본 원인을 반복적으로 제안해 당신이 하나하나 무효화해야 했고, 상당한 노력이 낭비되었습니다. Claude에게 결론을 내리기 전에 증거를 모으고 가설을 배제하도록 요청하면 이런 반복을 줄일 수 있습니다.
  • 푸시 알림 '재부팅 후' 버그에서, Claude는 결함 있는 가설들(A, M, V, AA)을 돌고 돌았고 당신이 기본적인 추론으로 무너뜨렸으며, 확정된 근본 원인에 끝내 도달하지 못했습니다(달성 못함).
  • 통화/푸시 알림 장애에서, Claude는 성급한 결론(서버 미발송, 그다음 Firebase 누락)에 이르렀고, 실제 distributor WebSocket 재연결 문제가 발견되기 전에 서버 팀이 헛수고를 하게 만들었습니다.
원하지 않은 자율적 행동
당신이 리뷰, 계획, 또는 수동 검증만 원했을 때도 Claude가 요청을 넘어 수정을 자동 적용하거나, 코드를 탐색하거나, 명령을 실행하는 경우가 잦았습니다. '리뷰만' 또는 '계획만, 구현하지 마'라고 미리 명시하면 Claude를 범위 안에 두는 데 도움이 됩니다.
  • 네이버 Z 과제에서 /review를 실행했을 때, 리뷰만 원했음에도 Claude가 수정을 자동 적용해 전부 되돌려야 했습니다.
  • 당신이 수동으로 검증하려 했을 때 Claude가 계속 실행/설치/강제 종료를 시도하고 wallet 경로를 탐색하려 해 '아니 됐고' 같은 인터럽트를 유발했습니다.
권한 차단과 셸 따옴표 처리 실패
자동 모드 분류기가 정당한 작업을 차단했고 채팅 UI 포맷팅이 명령을 손상시켜, 수동으로 실행하게 만들었습니다. 특정 명령 패턴을 사전 승인하고 단일 라인 또는 파일 기반 명령을 사용하면 이런 멈춤을 줄일 수 있습니다.
  • 분류기가 curl|bash 설치와 settings.json 자기 수정을 차단했고, 그다음 zsh의 '!' 히스토리 확장과 손상된 heredoc 때문에 터미널 명령을 여러 번 수동으로 실행해야 했습니다.
  • 상태표시줄에 model/effort를 추가하는 데 여러 번의 차단된 시도와 당신의 수동 터미널 실행을 거쳐서야 성공했습니다.

라이프사이클 이벤트에서 자동 실행되는 셸 명령.
당신에게 좋은 이유: 당신의 Android 세션은 빌드 검증에 크게 의존합니다(Bash가 1259회로 1위 도구였습니다). 편집 후 Gradle 빌드/포맷을 실행하는 post-edit hook은 스크롤바 modifier 순서 버그 같은 깨진 편집을 자동으로 잡아줍니다.
// .claude/settings.json { "hooks": { "PostToolUse": [ { "matcher": "Edit|Write", "hooks": [ { "type": "command", "command": "./gradlew ktlintFormat -q || true" } ] } ] } }

Claude Code를 활용하는 새로운 방법

이 내용을 Claude Code에 복사하면 단계별로 안내해줍니다.

권한 분류기 길들이기
settings.json 편집이나 설치 스크립트처럼 반복적으로 차단되는 도구와 명령을 사전 승인하세요.
여러 세션이 자동 모드 분류기가 settings.json 자기 수정, curl|bash 설치, heredoc을 차단하는 데서 멈췄고, 터미널에서 수동으로 명령을 실행하게 만들었습니다. 또한 zsh의 '!' 히스토리 확장과 채팅 UI 들여쓰기가 heredoc을 손상시키는 것과 싸웠습니다. 허용 도구/경로를 미리 설정하고 단일 라인 명령을 선호해 이 반복되는 비용을 피하세요.
Claude Code에 붙여넣기:
이것을 단일 라인 bash 명령으로 실행하세요(heredoc 없이, 멀티라인 없이). 그리고 zsh 히스토리 확장이 트리거되지 않도록 '!'를 피하세요: <command>
근본 원인 단정에서 속도 늦추기
디버깅에서 수정을 선언하는 대신 가설 배제 단계를 강제하세요.
당신의 최대 볼륨 목표는 디버깅(17개 세션)이었고, 최악의 결과(달성 못함, 좌절)는 Claude가 알림/푸시 버그에 대해 잘못된 근본 원인을 단정한 데서 비롯되었습니다. 성공한 세션들(메인 디스패처의 ANR, WebSocket 재연결, KeyManager 초기화)은 실제 메커니즘이 추적된 경우였습니다. 패치하기 전에 Claude가 원인을 증명하게 하세요.
Claude Code에 붙여넣기:
수정을 제안하기 전에, 가능한 모든 원인을 나열하고, 각각을 확인하거나 배제할 수 있는 증거가 무엇인지 말한 뒤, 내가 무엇을 확인해야 하는지 알려주세요. 아직 코드를 편집하지 마세요.
'계획'과 '실행' 분리하기
더 큰 작업에서는 Claude가 구현을 시작하지 않도록 계획만 하는 단계를 명시적으로 요청하세요.
Claude가 당신이 원하기 전에 구현이나 계획 작성을 시작했을 때, 그리고 계획이 확장성 고려사항을 놓쳤을 때 마찰을 겪었습니다. 당신의 큰 리팩토링(KMP 마이그레이션, 멀티 모듈)과 설계 질문을 고려하면, 게이트를 둔 계획 우선 접근이 낭비되는 편집을 방지하고 빈틈을 일찍 드러냅니다.
Claude Code에 붙여넣기:
이 작업에 대해 계획만 주세요. 엣지 케이스와 확장성 고려사항을 포함하세요. 코드를 작성하기 전에 내 승인을 기다리세요.

앞으로의 전망

당신의 워크플로우는 단일 파일 편집에서 진단, 멀티 파일 리팩토링, 빌드, PR, 리뷰 해결에 이르는 풀 사이클 Android/KMP 전달로 진화했으며, 이는 전체 엔지니어링 루프를 자율 에이전트에게 위임할 준비가 되었음을 시사합니다.

자율적 진단-수정-검증 디버그 루프
당신의 디버깅 세션(17개)은 실제 WebSocket/IPC 원인을 찾기 전에 성급한 근본 원인 추측(Firebase, 서버 미발송, IMPORTANCE_HIGH)에서 반복적으로 멈췄고 노력을 낭비했습니다. 자율 에이전트는 경쟁하는 가설들을 세우고, 로깅을 계측하고, 디바이스에서 재현하고, 실제 텔레메트리에 대해 각 분기를 반증한 뒤, 검증된 단일 수정안을 제시할 수 있습니다. 이는 몇 시간짜리 추측 마라톤을, 빌드가 통과되는 확정 진단만 드러내는 자기 교정 조사로 바꿉니다.
시작하기: 어떤 수정보다 먼저 증거 수집(logcat, git blame, 커밋 히스토리)에 전념하는 서브에이전트를 사용하고, 가설을 자동으로 검증하기 위해 재현과 빌드를 실행하도록 요구하세요.
Claude Code에 붙여넣기:
이 버그를 진단하세요: [증상 설명]. 어떤 수정을 제안하기 전에, 가능한 모든 근본 원인 가설을 열거하고 순위를 매긴 뒤, 각각에 대해 그것을 확인하거나 반증하는 구체적 증거(logcat, git log/blame, 코드 추적)를 수집하세요. 단 하나의 가설이 뒷받침 증거와 함께 살아남기 전까지는 수정을 제안하지 마세요. 그런 다음 수정을 구현하고, 빌드를 실행하고, 디바이스 재현을 실행해 검증하세요. 확정된 근본 원인과 검증된 결과만 보고하세요.
