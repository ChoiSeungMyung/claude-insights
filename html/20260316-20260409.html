사용 패턴 분석

당신은 Claude Code를 일상적인 Android 개발 워크플로우의 핵심 도구로 사용하는 높은 생산성의 수정 주도형 개발자입니다. 25일간 134개 세션에서 241개 커밋을 푸시했으며, 이는 하루 약 10개 커밋에 해당하는 놀라운 속도입니다. 일반적인 워크플로우는 버그 수정, PR 생성, 코드 리뷰 처리를 포함하며, 이를 단일 세션에서 연속으로 처리합니다. 상세한 사전 스펙을 제공하지 않고 간결한 작업 설명만 주며 Claude가 코드베이스를 탐색하고 알아서 해결하기를 기대합니다. Claude가 아키텍처 결정에서 실수할 때(자주 발생) 단호하게 방향을 수정하고 진행합니다.

가장 특징적인 점은 철저한 아키텍처 수호자라는 것입니다. 잘못된 접근 방식을 빠르게 포착하고(25건의 wrong_approach 마찰) 프로젝트 컨벤션을 위반하는 Claude의 제안을 주저 없이 거부합니다. 불필요한 try/catch 래핑, 잘못된 언어의 코멘트, develop 브랜치에 대한 실수 커밋 등이 그 예입니다. 이런 마찰에도 불구하고 만족도는 매우 높고(129건 만족) 성공률도 우수합니다(분석된 50건 중 39건 완전 달성). 이는 Claude를 빠르지만 가끔 부주의한 주니어 개발자로 다루는 법을 터득했음을 시사합니다. Bash(3,044회)와 Read(1,822회) 도구를 많이 사용하여, 코드 편집만이 아닌 실제 디바이스에서의 빌드, 배포, 검증을 원함을 보여줍니다.

핵심 패턴: 구현은 Claude에게 위임하되 아키텍처 오류를 적극적으로 개입하여 수정하는 빠르게 움직이는 테크 리드로서, Claude를 생산적이지만 아키텍처적으로는 경험이 부족한 페어 프로그래머로 활용합니다.

문제 발생 지점

세션 전반적으로는 성공적이지만, Claude가 잘못된 아키텍처 결정을 내리거나 솔루션을 과도하게 복잡하게 만들거나 근본 원인을 잘못 진단하면서 상당한 시간이 낭비되고 있습니다.

단순한 해법 대신 잘못된 접근
Claude가 더 단순한 솔루션이 있을 때 반복적으로 과도하게 복잡하거나 잘못된 솔루션을 시도하여 여러 번의 수정 라운드가 필요합니다. 초기 프롬프트에서 제약 조건이나 원하는 접근 방식을 명시하면 상당한 왕복을 줄일 수 있습니다.
  • IME 닫기 탭 처리에서 Claude가 잘못된 파일, 잘못된 이벤트 핸들링, 과도하게 복잡한 커스텀 포인터 로직을 여러 차례 시도한 후에야 사용자가 간단한 detectTapGestures 솔루션으로 유도
  • Claude가 Maven 퍼블리싱을 위해 프로젝트 구조를 과도하게 탐색하고 RC 마이그레이션 분석을 과도하게 복잡화하여, 생산적인 작업이 시작되기 전 여러 번 접근 방식을 리디렉션해야 했음
아키텍처 및 코드베이스 오해
Claude가 domain 레이어 순수성이나 git 브랜칭 규칙 같은 프로젝트의 아키텍처 컨벤션을 자주 위반합니다. 이러한 제약 조건을 명시적으로 문서화한 CLAUDE.md나 시스템 프롬프트가 도움이 될 수 있습니다.
  • Claude가 domain 레이어에 Android 의존성을 추가하고 불필요한 별도의 repository를 주입하려 해서, 한 세션에서 아키텍처를 두 번 수정해야 했음
  • Claude가 feature 브랜치 대신 develop에 직접 커밋하고 이후 요청 없이 develop에 머지하여, cherry-pick과 롤백이 필요했음
잘못된 근본 원인 진단
Claude의 초기 진단이 종종 틀려서 실제 문제가 식별되기 전에 헛된 수정 반복이 발생합니다. 구현 전에 가능성 순으로 정렬된 여러 가설을 제시하도록 요청하면 이런 잘못된 시작을 줄일 수 있습니다.
  • 알림 배지 문제에서 Claude는 기능이 완전히 활성화되어 있고 사용자 권한 누락이 원인이라고 주장했지만, 실제 문제는 시스템 UID 앱에 필요한 enabled_notification_listeners 등록 누락이었음
  • 유령 통화 알림 버그에서 Claude가 처음에는 sync-first 레이스 컨디션을 원인으로 지목했지만, 로그 분석 결과 푸시가 늦게 도착한 것이 원인이었고, 이후 쿨다운 기반 수정을 시도한 뒤에야 올바른 상태 체크 접근 방식에 도달

CLAUDE.md 추가 제안 사항

Claude Code에 복사해서 붙여넣으면 CLAUDE.md에 추가됩니다.

명시적으로 요청하지 않는 한 버전 범프, 의존성 변경 또는 설정 수정을 하지 않습니다. 변경 사항은 요청된 범위로 최소화합니다.

Custom Skills (커스텀 스킬)
단일 /command로 실행되는 재사용 가능한 프롬프트 워크플로우
추천 이유: commit-pr과 agent-review 스킬을 이미 많이 사용하고 있습니다(20+ 커밋/PR 세션, 13+ 리뷰 처리 세션). 아키텍처 규칙이 내장된 /fix 스킬을 만들면 domain 레이어 순수성과 과도한 엔지니어링 관련 반복적인 마찰을 방지할 수 있습니다.
mkdir -p .claude/skills/fix && cat > .claude/skills/fix/SKILL.md << 'EOF' # Fix Skill 1. 필요한 최소한의 변경만 식별 - 추가 리팩토링 금지 2. Domain 레이어: 순수 Kotlin만, Android import 금지 3. 수정이 컴파일되는지 빌드 및 확인 4. develop에 머지하거나 버전 범프 금지 5. 사용자에게 확인: 브랜치 + PR 생성, 아니면 커밋만? EOF
Hooks (훅)
pre-commit 같은 라이프사이클 이벤트에서 쉘 명령을 자동 실행
추천 이유: 241개 커밋과 잘못된 브랜치에 커밋하거나 빌드 체크를 잊는 반복적인 문제가 있으므로, 현재 브랜치를 검증하고 빌드 체크를 실행하는 pre-commit 훅이 실수를 사전에 방지합니다.
// .claude/settings.json에 추가 { "hooks": { "PreToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command", "command": "if echo \"$CLAUDE_TOOL_INPUT\" | grep -q 'git merge\\|git push.*develop\\|git push.*main'; then echo 'BLOCK: 명시적 사용자 승인 없이 develop/main에 머지 또는 푸시 금지' && exit 1; fi" } ] } ] } }
Headless Mode (헤드리스 모드)
자동화 작업을 위해 Claude를 비대화형으로 실행
추천 이유: 9개 이상의 빌드/배포 세션과 빈번한 PR 리뷰 사이클을 처리합니다. CI에서 리뷰 코멘트 해결이나 린트 수정을 자동화하면 반복적인 워크플로우에서 상당한 시간을 절약할 수 있습니다.
claude -p "현재 PR의 미해결 리뷰 코멘트를 모두 읽고, 각각 최소한의 변경으로 수정하고, 푸시하고, 각 스레드에 답장" --allowedTools "Bash,Read,Edit,Write,Grep"
