Claude Code 사용 방식

당신은 주로 Android/Kotlin 개발(집중적인 Compose UI 작업, KMP 마이그레이션, Matrix/메신저 기능)을 하며, 지배적인 작업 방식은 촘촘한 교정 감독과 결합된 진단형 디버깅입니다. 상세한 사전 스펙을 작성하기보다 증상이나 목표(버그, 재현할 Figma 스크린샷, 빌드 실패)를 서술하고 Claude가 조사하게 한 뒤, 공격적으로 방향을 수정합니다. 마찰 데이터가 이를 명확히 보여줍니다: 세션을 반복적으로 중단시켰고(코드베이스 탐색에서 웹 리서치로 방향 전환, 진단이 끝나기 전에 Claude를 정지, 수동 검증을 원할 때 자율적인 실행/설치/강제 종료 시도를 차단), 높은 Bash 사용량(1588)과 73개 세션에 걸친 68개 커밋은 실제 빌드-커밋-PR 루프를 운영하며 Claude가 성공을 주장만 하는 것이 아니라 실제 빌드로 작업을 검증하길 기대함을 나타냅니다.

두드러진 특징은 Claude의 결론을 액면 그대로 받아들이지 않는다는 점입니다. 잘못된 Kotlin/Metro 버전 조합을 바로잡았고, api/impl 분리에 대한 Claude의 주장을 반박하기 위해 공식 문서를 제시했으며, 목업에서 Claude가 누락한 'Get Started' 버튼을 지적했고, 지나치게 선명한 색상과 잘못 클릭 가능하게 만든 카드를 거부했습니다. 만족도 분포(159 '만족 추정' 대 32 '불만족')와 마찰 카테고리 — 잘못된 접근(33), 버그 있는 코드(22), 요청 오해(19) — 는 상호작용의 상당 부분이 Claude의 성급하거나 잘못된 근본 원인 주장을 잡아내는 일이었음을 반영합니다. Claude의 반복된 잘못된 결론(서버 미전송, 그다음 Firebase)이 실제 원인인 distributor WebSocket이 발견되기 전에 서버 팀의 노력을 낭비시킨 알림 실패 세션은, 당신이 Claude를 짧은 고삐로 통제하는 이유를 가장 명확하게 보여주는 사례입니다.

또한 상당한 반복적 문서 다듬기(15 세션)를 수행하며, 여기서는 더욱 까다롭습니다: 지나치게 낙관적인 초안, 근거 없는 동의, 프레이밍 문제를 밀어붙여 그룹 채팅 기획 문서와 백서 갭 분석에서 여러 차례의 교정 라운드를 요구했습니다. 코드와 산문 모두에서 패턴은 동일합니다 — Claude의 첫 답변을 결과물이 아니라 심문할 초안으로 취급합니다. AskUserQuestion(115)과 Task 추적에 의존하지만, 속도를 늦추면 그것들도 중단시킵니다. 31일 동안 455시간이라는 수치는 짧은 단발성 작업이 아니라 길고 깊은 작업 세션을 의미합니다.

핵심 패턴: 증상을 서술하고 Claude가 조사하게 한 뒤 촘촘히 감독합니다 — 중단시키고, 빌드를 직접 검증하고, 첫 답변을 신뢰하는 대신 Claude의 성급하거나 잘못된 결론을 교정합니다.

문제가 생기는 지점

주요 마찰은 성급한 결론과 되돌려지는 자율적 행동, 그리고 수동 우회를 강제하는 환경적 장애(auto-mode 분류기, 토큰 제한, 보호된 페이지)에서 옵니다.

디버깅에서의 성급한 근본 원인 결론
가장 빈번한 워크플로우는 디버깅(31 세션)이며, 반복되는 실패는 Claude가 검증 전에 잘못된 진단을 확정하는 것입니다. 근본 원인 선언 전에 더 강한 증거를 요구하는 것 — 특히 다른 사람의 작업을 유발하는 경우 — 이 낭비되는 노력을 줄여줄 것입니다.
  • 푸시/통화 알림 세션에서 Claude는 실제 원인인 distributor WebSocket 재연결 문제 이전에 두 개의 잘못된 결론(서버 미전송, 그다음 Firebase 누락)에 도달했고, 이는 서버 팀의 노력 낭비와 사용자 불만을 야기했습니다.
  • 앱 실행 실패 세션에서 Claude의 초기 가설에 대한 확신 때문에 여러 버그(빈 미리보기, 편집 미반영)가 부분적으로만 수정되어 추가 반복이 필요했습니다.
교정되거나 거부되는 자율적 행동
17건의 거부된 행동과 33건의 잘못된 접근 플래그는 Claude가 범위 확인 전에 행동하는 경우가 많음을 나타냅니다 — 계획만 원했는데 구현하거나, 수동 검증을 원했는데 실행하는 식입니다. 시작 시 의도(계획 대 구현, 자동 대 수동)를 확인하면 재작업을 피할 수 있습니다.
  • 수동 검증을 원했는데 Claude가 반복적으로 강제 종료, 지갑 경로 탐색, 앱 실행을 스스로 시도했고, 계획만 원한다고 명확히 하기 전에 구현을 시작했습니다.

CLAUDE.md 추가 제안

이 내용을 Claude Code에 복사하면 CLAUDE.md에 추가해 줍니다.

여러 세션(푸시/통화 알림, 온보딩, 채팅 목록)에서 Claude가 성급하게 잘못된 근본 원인에 도달해 서버 팀을 포함한 실제 노력을 낭비시켰습니다.
사용자가 수동 검증을 원할 때 Claude가 자율적으로 실행/설치/탐색하며 발생한 마찰이 여러 세션에서 나타났습니다.
스크린샷 기반 Compose 화면에서 'Get Started' 버튼 등 요소가 반복적으로 누락되어 사용자가 잡아내야 했습니다.
거의 모든 세션이 Android/Compose/Matrix이고, 빌드 검증이 성공적인 결과와 상관관계가 있었으며, Play Store 준비 점검 중 AGPLv3 컴플라이언스 리스크가 발생했습니다.

이 내용을 Claude Code에 복사하면 알아서 설정해 줍니다.

Custom Skills
Markdown으로 저장되는 재사용 가능한 /command 프롬프트.
당신에게 필요한 이유: 이미 'agent-review' 스킬을 최소 3개의 PR 리뷰 세션에서 성공적으로 사용했습니다. 커밋/PR/리뷰 루프를 스킬로 공식화하면 68개 커밋 규모 작업에서 반복되는 준비 작업을 줄일 수 있습니다.
# .claude/skills/review/SKILL.md PR 리뷰 코멘트를 가져와 각 스레드를 코드 수정으로 대응하고, 빌드로 검증한 뒤, 각 스레드에 답변하고 해결 처리하고, 커밋 후 푸시하세요. 내 승인 없이 스레드를 해결 처리하지 마세요.
Hooks
라이프사이클 이벤트에서 자동 실행되는 셸 명령.
당신에게 필요한 이유: 빌드를 직접 검증하며 R8 OOM과 proguard 실패를 겪었습니다. 편집 후 빌드/린트를 실행하는 hook이 있으면 요청하기 전에 회귀를 잡아낼 수 있습니다.
// .claude/settings.json { "hooks": { "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{"type": "command", "command": "./gradlew ktlintCheck -q || true"}] }] } }
Task Agents
탐색이나 병렬 작업을 위한 집중형 서브에이전트.
당신에게 필요한 이유: 디버깅 세션에서 수정 전에 다중 파일 코드 경로 추적이 반복적으로 필요합니다. 전용 탐색 에이전트는 진단 단계를 편집과 분리해 성급한 결론을 줄여줍니다.
에이전트를 사용해 CallDecline부터 재벨울림까지의 전체 코드 경로를 추적하고, 수정안을 제안하기 전에 근본 원인의 증거를 보고하세요.

성급한 근본 원인 결론 방지하기
디버깅 세션(31개)이 최상위 목표였지만, Claude가 초기에 잘못된 근본 원인에 매달려 여러 세션이 정체됐습니다 — 한 사례는 실제 WebSocket 재연결 문제가 드러나기 전에 서버 팀의 시간을 낭비시켰습니다. 수정안 제시 전에 증거 수집과 가설 순위화를 강제하는 워크플로우가 이를 줄일 수 있으며, 자율성만 늘린다고 디버깅이 나아진다고 가정해서는 안 됩니다. 현실적인 이득은 완전히 손 놓는 디버거가 아니라 잘못된 단서의 감소입니다.
시작하기: 로그/재현 수집에 Bash를 사용하는 구조화된 디버깅 프롬프트를 쓰고, 편집 전에 Claude가 확신 수준을 명시하도록 요구하세요. 이는 데이터에 나타난 특정 실패 패턴을 겨냥한 것이지, 일반적인 '알아서 하게 두기' 접근이 아닙니다.
Claude Code에 붙여넣기:
이 버그의 수정안을 제안하기 전에 다음을 순서대로 수행하세요: (1) Bash로 로그/테스트에서 재현하거나 구체적인 증거를 수집, (2) 각각의 찬반 증거와 함께 최소 두 개의 경쟁하는 근본 원인 가설을 나열, (3) 확신도 순으로 순위를 매기고 최상위 가설을 확인할 추가 증거가 무엇인지 알려주기, (4) 내가 가설을 확인하기 전까지 코드를 편집하지 않기. 증거가 불충분하면 추측하지 말고 그렇다고 말하세요.
