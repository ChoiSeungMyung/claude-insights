Claude Code 사용 방식

당신은 개별 수정이 아니라 워크플로우 전체를 위임하는 오케스트레이터로 일합니다. 전형적인 요청은 여러 단계를 지시 하나에 묶습니다. PR 코멘트를 해결하고, rebase하고, 지적이 0건이 될 때까지 로컬 리뷰를 돌리고, PR을 열고, 로컬 Maven에 배포하고, 1.1.1 릴리스를 만들고, 머지된 worktree를 정리하라는 식입니다. 도구 사용 비율도 이를 뒷받침합니다. 사용자 메시지는 790개뿐인데 Bash 호출은 3,557회, Agent 생성은 188회이므로, 대부분은 Claude가 긴 자율 실행을 이어 가도록 맡깁니다. cron 루프, pr-watch, Orca 코디네이터 작업, 리뷰어 두 명이 7라운드를 도는 사이클이 그 예입니다. 단계마다 승인하지 않습니다. 약 30일 기간에 1,882시간이 기록된 것은 실제 경과 시간(약 720시간)보다 깁니다. 이는 여러 세션이 병렬로 돌았다는 강한 신호입니다. 긴 대화 하나가 아니라 실제로 여러 세션을 병렬로 운영하고 있습니다.

처음 주는 지시는 짧고 결과 중심입니다. '코멘트 0건까지 리뷰한 다음 PR'이나 '머지된 worktree 정리, 브랜치는 유지' 같은 식입니다. 세부 규칙은 실행 도중의 교정으로 나타납니다. PR 단위(API당 PR 하나)를 정해 주고, 'n차 리뷰 반영' 커밋을 금지하고, PR을 이해하는 데 필요한 커밋만 남기게 하고, 작업 시작 전에 develop으로 rebase하게 하고, 리뷰 답글은 한국어로 쓰게 하고, 범위를 제한했습니다(NM-191만, 세션 밖 PR은 제외). 마찰 데이터도 이를 반영합니다. wrong_approach(24)와 misunderstood_request(19)가 buggy_code(15)보다 확실히 많습니다. 당신의 지적은 대부분 코드 정확성보다 프로세스, 범위, 컨벤션에 관한 것입니다. Claude가 망설일 때 당신의 답은 짧고 단호했습니다. 'Orca가 만든 거니까 그냥 지워'라고 하거나, 버그 재현을 당신에게 부탁하지 말고 직접 하라고 한 것이 그 예입니다. 당신은 Claude가 수동 절차를 떠넘기지 않고 디바이스와 리포에서 직접 움직이기를 기대합니다.

당신은 또한 추측을 사실로 받아들이지 않습니다. iOS PR #153에서 놓친 리뷰 항목을 잡아냈고, 대상 프로젝트의 AGENTS.md를 읽지 않고 쓴 핸드오프 문서에 반박했습니다. 가장 많이 다룬 파일 유형은 Markdown(203)인데, 이는 코드만큼이나 문서와 규칙 파일을 많이 다뤘다는 뜻입니다. 전반적인 만족도는 긍정 쪽입니다(만족 추정 165 대 불만족·불만 심함 35). 남은 불만은 Claude의 기술 역량보다는, 말하지 않은 워크플로우 컨벤션을 Claude가 무시한 데 몰려 있습니다.

핵심 패턴: 여러 단계로 된 긴 워크플로우를 Claude에게 자율 실행하도록 맡기고, 흔히 병렬 세션으로 돌립니다. 개입할 때는 주로 코드를 고치기보다 프로세스 규칙(PR 단위, 커밋 정리, 범위, 언어)을 지키게 합니다.

인상적인 작업들

약 한 달 동안 41개 세션에서 Claude Code를 주로 Android/iOS 통화 앱 개발에 썼습니다. PR 리뷰 처리, 릴리스, 디바이스 디버깅, worktree 관리가 중심이었고, 커밋은 110개, 41개 세션 중 35개가 대부분 또는 완전 달성이었습니다.

지적 0건까지 가는 로컬 리뷰 루프
PR을 열기 전에 리뷰어들이 지적 0건을 보고할 때까지 로컬 리뷰와 수정을 반복하라고 자주 요구했습니다. 한 번은 리뷰어 두 명씩 7라운드가 걸렸고, 수정 사항은 mutation test로 확인했습니다(PR #183). 같은 규칙을 PR #200, PR #17, NM-191 작업에도 적용해 사람이 리뷰하기 전에 문제를 잡았습니다. 다만 NM-191 iOS PR은 해결되지 않은 테스트 실패 4건을 안은 채 올라갔으므로, 실패한 테스트도 PR 생성을 막도록 하면 이 관문이 가장 잘 동작합니다.
디바이스 증거 기반 근본 원인 디버깅
통화와 메시징 실패에서는 추측 대신 실제 디바이스에서 증거를 모으게 했습니다. 두 디바이스의 logcat은 SIM이 없는 디바이스가 locale로 국가를 판단해서 생긴 KR/US LiveKit 서버 불일치를 보여 줬습니다. XCUITest 재현으로 iPhone의 오래된 sync v2 토큰을 찾았습니다. AOSP 소스는 설정 중에 device_provisioning_mobile_data 플래그가 꺼져 있었음을 보여 줬고, AOSP 개발자가 이를 확인했습니다. 각 경우 수정은 관찰된 동작에 비춰 검증됐습니다. 하지만 heads-up 깜빡임 수정, SIM 삽입 온보딩 상태, SFU 수정처럼 이후의 몇몇 수정은 디바이스에서 확인하지 않았습니다. 그 단계를 더하면 검증 고리가 완성됩니다.
리포를 넘나드는 라이브러리→앱 릴리스 흐름
변경을 전체 체인에 걸쳐 옮기는 데 Claude를 씁니다. 통화 엔진 변경은 리뷰와 rebase를 거쳐 로컬 Maven에 배포되고 GitHub Packages로 릴리스됩니다(1.1.0, 1.1.1, 1.2.0). 그다음 Android와 iOS 앱 양쪽에서 새 버전으로 올리고, 연결된 디바이스에 Stg 또는 프로덕션 빌드를 설치하고, 머지된 worktree를 정리합니다. 이 과정을 Orca, 병렬 에이전트(Agent 호출 188회), SendMessage로 조율합니다. 작업 전 develop rebase, API당 PR 하나, 머지된 worktree는 브랜치로 남기기 같은 규칙도 만들었습니다. 이 규칙들은 아직도 자주 다시 교정되고 있으므로, CLAUDE.md나 AGENTS.md에 적어 두면 같은 말을 반복하는 일이 줄어듭니다.

문제가 생기는 지점

마찰은 대부분 두 가지 패턴에서 나옵니다. Claude가 사실을 확인하지 않고 빈 곳을 추측으로 채우는 것과, git·PR 컨벤션을 세션마다 다시 말해야 하는 것입니다.

사실과 맥락을 확인하지 않고 추측하기
Claude는 확인하지 않은 내용을 쓰거나 예측하는 일이 잦았습니다. 핸드오프 문서의 대상, 충돌 예측, 기본값이 그랬고, 당신이 직접 잡아내 바로잡아야 했습니다. Claude에게 대상 프로젝트의 AGENTS.md/CLAUDE.md와 소스 코드를 먼저 읽게 할 수 있습니다. 또 최종본을 쓰기 전에 확인할 수 없는 내용은 추측이라고 표시하거나 당신에게 묻게 할 수도 있습니다.
