Claude Code 사용 방식

당신은 한 단계씩 짝 프로그래밍하는 사람이 아니라 워크플로우 전체를 위임하는 사람으로 일합니다. 69개 세션에 걸친 약 998개 메시지에 비해 Bash 호출이 5,700회 가까이 된다는 것은, 프롬프트 하나가 보통 긴 자율 실행을 일으킨다는 뜻입니다. 요청은 최종 상태를 정한 계약서처럼 읽힙니다: "프로젝트 전체를 단순화하고, 코멘트가 0이 될 때까지 로컬에서 리뷰하고, squash하고, PR을 열어." 그러면 Claude는 PR #9가 나가기까지 22라운드의 리뷰를 돌렸습니다. 모듈 그래프 경계 수정에도 같은 형태를 썼고(12라운드 후 PR #163), core/local 정리도 PR #161로 끝났습니다. 0건이 될 때까지 리뷰하는 루프가 당신의 시그니처 패턴입니다. 이 루프는 /agent-review, worktree, Copilot 스레드 resolve로 돌아갑니다. 상위 목표가 code_review, PR 코멘트 대응, 커밋·PR 작업이라는 점은 시간 대부분이 기능을 처음부터 쓰는 데가 아니라 리뷰 사이클을 마무리하는 데 쓰인다는 것을 보여줍니다. 이 루프에는 당신이 감수하는 비용이 있습니다. Claude 자신의 수정이 회귀를 만들거나 이전 라운드와 모순되는 경우가 잦았는데, 라운드마다 새 코멘트를 부른 room-wait 코드와 왔다 갔다 한 konan 캐시 키가 그 예입니다. buggy_code와 wrong_approach가 마찰 1위로 동률(각 27건)인 이유도 여기서 일부 설명됩니다.

실행 도중 끼어드는 일은 드물지만, 끼어들 때는 짧고 직설적이며 교정적입니다. 조용히 돌아가는 백그라운드 빌드 중에 보낸 '루프 정지해', '너 뭐하니?' 같은 메시지가 그 예입니다. 교정은 코드 세부보다 범위와 전제에 맞춰져 있습니다. AGENTS.md 업데이트가 필요 없다고 했고, 별도 통합 PR 대신 PR #8의 대상 브랜치를 develop으로 바꾸면 된다고 짚었고, keychain 수정은 실제 사용자가 아니라 개발자에게만 영향이 있다고 지적했습니다. Claude가 잘못 잡은 사실 전제도 잡아냈습니다: 칩은 Qualcomm SoC가 아니라 Rockchip RK3527이었고, 통화 SDK에는 iOS 소비자가 있으며 음성 전용은 의도된 범위였습니다. 반대 방향도 자주 일어납니다. 당신의 질문 자체에 흔들리는 전제가 담긴 경우가 많았고 Claude가 이를 바로잡았습니다: Location은 API가 아니라 data class이고, GitHub '로그인 오류'는 실제로는 계정 정지였고, 재발신 버그 문서는 실제 원인보다 범위가 좁았습니다. 당신은 이런 교정을 마찰 없이 받아들입니다.

당신의 작업은 실제 환경을 직접 다룹니다. iPhone XR에 빌드를 설치하고, non-GMS 하드웨어에서 adb 진단을 돌리고, 2대 디바이스 자동 통화 테스트를 하고, iPhone 통화 지연을 7–34초에서 0.5–1.8초로 줄이고, Maven Local과 패키지 레지스트리에 배포합니다. worktree·브랜치 정리, cron으로 도는 /nm-ticket 루프 같은 운영성 잡무도 Claude에 많이 맡깁니다. "남은 결정 세 가지는 네가 내려"나 "push해"처럼 넓은 권한을 주는 일도 잦습니다. 그 신뢰가 가끔 역효과를 냈습니다: Claude가 다른 세션의 커밋을 develop에 push했고, 결함 있는 검증 스크립트 때문에 App Store 작업 전체를 되돌렸습니다. 69개 세션에 기록된 1,310시간은 실제 타이핑 시간이라기보다 오래 열어 둔 세션이나 루프 세션을 반영할 가능성이 큽니다. 당신의 실질적인 입력은 빈도는 낮고 레버리지는 큰 방향 지시입니다.

핵심 패턴: 처음부터 끝까지의 결과 계약 — 특히 코멘트 0건이 될 때까지 수정 → 리뷰 → 수정을 반복하고 PR로 끝나는 루프 — 을 Claude에 넘기고, 궤도를 벗어날 때만 범위나 전제에 대한 짧은 교정으로 개입합니다.

인상적인 작업들

한 달 동안 69개 세션(998개 메시지, 227개 커밋)에서 당신은 Claude Code를 주로 Android, iOS, TypeScript 통화·메시징 스택 전반의 코드 리뷰, PR 코멘트 해결, 온디바이스 디버깅에 썼습니다.

코멘트 0건까지 가는 리뷰 루프
'코멘트가 0건이 될 때까지 로컬 리뷰와 수정을 반복'이라는 명확한 종료 조건을 자주 정한 뒤, Claude에게 커밋 squash, PR 생성, 각 스레드 답글과 resolve까지 맡겼습니다. 이렇게 22라운드 리뷰 끝에 PR #9가, CI를 통과한 12라운드 끝에 PR #163이 나왔고, PR #22, #161, #51에서도 비슷한 결과가 나왔습니다. 작업을 별도 worktree에서 돌리고 끝난 뒤 머지된 브랜치를 정리한 덕분에 병렬 작업끼리 충돌하지 않았습니다. 다만 README push 한 번은 다른 세션의 커밋을 실수로 포함했습니다.
Mutation testing으로 테스트 감사
커버리지를 테스트가 쓸모 있다는 증거로 보지 않았습니다. 대신 Claude에게 Pitest와 mutation 패스(한 번은 768개 테스트 대상 2,507개 mutant)를 돌려, 아무것도 잡아내지 못하거나 앱 코드를 전혀 건드리지 않는 테스트를 찾게 했습니다. 수정 단계는 테스트 코드로 한정했고, 결과는 더 강한 테스트와의 비교를 곁들인 공유 문서로 발행하게 했습니다. 그 결과 추측이 아니라 측정된 수치 — 실제로 약한 테스트 약 1% — 를 얻었습니다.

Hooks
git push 같은 특정 도구 호출 전에 가드 스크립트를 자동으로 실행합니다.
왜 필요한가: develop에 엉뚱한 커밋을 push한 일이 이미 한 번 있었고, 당신은 많은 세션과 worktree를 병렬로 돌립니다. PreToolUse hook이 push될 커밋을 보여 주면, 남의 커밋이 원격에 닿기 전에 잡을 수 있습니다.
// .claude/settings.json { "hooks": { "PreToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command", "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/pre-push-check.sh" } ] } ] } } # .claude/hooks/pre-push-check.sh #!/bin/bash cmd=$(jq -r '.tool_input.command') if echo "$cmd" | grep -q 'git push'; then git fetch -q echo 'Commits to be pushed:' >&2 git log --oneline @{u}..HEAD >&2 2>/dev/null fi exit 0

가장 가치 있었던 디버깅은 실제 디바이스에서 나왔습니다: sliding sync를 깨뜨린 sync v2 폴링(7-34초에서 0.5-1.8초로), 위젯 타임라인 상태 때문에 생긴 iOS 벨 미울림, 재발신 벨 미울림, 그리고 사람이 개입하는 바람에 결과를 버려야 했던 2대 디바이스 adb TC 실행. 전용 하네스가 있으면 짝지은 Android(adb)와 iOS(xcrun devicectl) 디바이스에서 스크립트로 통화 시나리오를 돌리고, logcat과 os_log 타임라인을 캡처하고, 통화 연결 지연과 벨 성공률을 계산할 수 있습니다. 그러면 에이전트가 지표가 목표에 닿을 때까지 커밋을 bisect하거나 후보 수정을 자율적으로 시도할 수 있습니다. 모든 통화 엔진 PR이 '디바이스에서 검증 안 됨'이 아니라 측정된 전후 수치를 갖고 올라오게 됩니다.
