Claude Code 사용 방식

당신은 빠르고 반복적인 페이스와 긴밀한 피드백 루프로 작업합니다. Claude Code를 자율 에이전트가 아닌 직접 협업하는 동료로 다룹니다. 세션은 Bash(3,958회)와 Edit(1,902회) 작업이 지배적이며, 295시간 동안 213개 커밋을 출시했습니다 — 빅뱅 배포보다 지속적 통합을 선호한다는 명확한 신호입니다. PR 리뷰 코멘트를 체계적으로 처리하기 위해 `agent-review` 스킬 같은 구조화된 워크플로우를 자주 호출하고, `ExitPlanMode`를 132번 사용해 Claude의 계획을 본 후에 실행하도록 하는 것을 중시합니다. Claude가 의도를 잘못 읽었을 때 — 리뷰를 요청했는데 코드를 자동 수정하거나, 실제 서버 응답 대신 mock 데이터를 검토할 때 — 날카롭게 중단시키고 방향을 바꿉니다 (한국어 '아니 됐고' 순간이 상징적). 나쁜 접근이 누적되도록 두지 않습니다.

당신은 디버깅에 깊이 관여하며 Claude의 추론이 약할 때 망설임 없이 반박합니다. 푸시 알림 세션에서 Claude가 제안한 가설 A, M, V, AA를 차례로 무력화시켜, 당신이 적용하는 동일한 기본 추론을 Claude에게도 기대한다는 것을 보여줬습니다. 마찬가지로 Claude가 의도적인 DTO 필드 변경을 되돌리거나, 잘못된 브랜치로 전환해 stash된 작업을 잃거나, 명시적 메모리 규칙에 반해 로그를 추가한 것을 잡아냈습니다. 이는 당신이 신뢰하되 적극적으로 검증한다는 것을 시사합니다 — 다중 파일 리팩토링(19개 성공)에서 Claude를 자유롭게 두지만, 궤도를 벗어나는 순간을 경계합니다. UI/UX 작업은 특히 반복적입니다: AlarmCard 리디자인, 드래그 핸들 물리, 해커톤 발표 페이지 모두 피드백 기반의 시각적 개선 라운드를 여러 번 거쳤습니다.

당신의 워크플로우에는 독특한 '출시하자(ship it)' 리듬이 있습니다: 구현 → 빌드 검증 → 커밋 → PR → 리뷰 코멘트 처리, 종종 루프를 닫기 위해 `agent-review` 호출. 높은 만족률(만족 132 vs 불만족 31)과 34개의 '잘못된 접근' 마찰 이벤트가 결합되어, 전체 속도가 높게 유지되는 한 Claude의 실수를 용인하는 사람으로 보입니다. 상세한 사전 명세를 거의 작성하지 않고, 대신 목표 결과를 (종종 스크린샷 참조와 함께) 설명하고, Claude가 시도하게 한 후 대화를 통해 개선합니다 — 2~3회의 반복이 한 번에 완벽하게 명세하는 것보다 종종 더 빠르다는 것을 받아들입니다.

핵심 패턴: 긴밀하고 출시 중심의 루프를 주도하면서 지속적으로 방향을 보정합니다 — Claude가 자율적으로 작업을 시도하게 두되, 추론이나 접근이 표류하는 순간 단호하게 중단시킵니다.

문제가 발생하는 지점

전반적인 완료율은 높지만, 작동하는 코드에 도달하기 전 성급한 해결 시도, 범위/브랜치 혼동, 도구 실행 실수에서 오는 마찰이 반복됩니다.

조사 전에 근본 원인 추측하기
Claude의 첫 시도 가설이 틀린 것으로 판명되어 하나씩 무효화시키는 일이 자주 발생합니다. 대신 Claude가 수정을 제안하기 전에 증거(로그, 런타임 데이터, 작동하는 코드와의 비교)를 수집하도록 요청하세요.
  • 재부팅 후 푸시 알림 버그에서 Claude는 가설 A/M/V/AA를 순환했고, 당신이 기본 추론으로 모두 무력화시켜 결국 '미달성'으로 끝남
  • TextField 지터 버그는 Claude가 기존에 작동하는 다이얼로그와 비교하기 전까지 많은 추측 기반 시도가 실패함 — '보통 도움됨' 결과를 얻기까지 시간 낭비
범위 드리프트와 원치 않는 부수적 변경
Claude는 요청한 것보다 더 많이 하는 경향이 있습니다 — 리뷰 중 수정을 자동 적용하거나, 메모리 규칙에 반해 로그/테스트를 추가하거나, 무관한 코드를 수정합니다. '분석 전용' vs '변경 적용'을 더 명시적으로 사전 지정하고, 리뷰형 커맨드를 잠그는 것을 고려하세요.
  • /review가 당신이 리뷰만 원했는데 중대한 이슈를 자동 수정해, 변경 전체를 되돌려야 함
